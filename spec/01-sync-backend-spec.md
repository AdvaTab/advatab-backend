# SupaTabs — Phase 1 Specification: Sync Backend

**Status:** Implementation specification  
**Phase:** 1 of 3  
**Primary target:** Cloudflare Workers + SQLite-backed Durable Objects  
**Protocol:** SupaTabs Sync Protocol v1  
**Last updated:** 2026-08-30

---

## 1. Purpose

Implement the storage and synchronization backend for SupaTabs.

The backend is intentionally **application-agnostic**. It MUST NOT understand tabs, tab groups, URLs, titles, notes, tags, or other SupaTabs domain objects. It stores opaque encrypted records and coordinates synchronization between trusted devices.

Phase 1 MUST be independently usable before the managed SupaTabs Cloud account/billing system exists.

### Phase 1 provides

- One vault represented by one SQLite-backed Durable Object.
- Revisioned opaque record storage.
- Incremental push + pull synchronization.
- Optimistic concurrency control.
- Tombstone deletion.
- Idempotent sync requests.
- Device public-key authentication.
- Generic encrypted key-envelope storage.
- Temporary device-pairing mailbox.
- Bootstrap mechanism for development/BYO deployments.
- Protocol discovery and versioning.

### Explicitly out of scope

- SupaTabs Cloud customer accounts.
- Billing/subscriptions.
- Email.
- A global user directory.
- Managed-cloud passkey discovery.
- Passkey PRF key envelopes.
- D1 control plane.
- Any parsing/decryption of synchronized records.

Those belong to Phase 3 unless otherwise noted.

---

## 2. Architectural principles

1. **The extension is trusted; the server is not trusted with plaintext.**
2. **The server stores opaque ciphertext.**
3. **One logical vault maps to one Durable Object.**
4. **The Durable Object serializes mutations and owns the vault revision counter.**
5. **Server revisions are authoritative and monotonically increasing.**
6. **Clients use optimistic concurrency per item.**
7. **Bootstrap and incremental sync use the same `/sync` endpoint.**
8. **All mutating API operations must be idempotent or safely retryable.**
9. **Authentication and encryption are independent.**
10. **No conventional server sessions, cookies, passwords, or refresh tokens are required.**
11. **The sync protocol must remain portable to a non-Cloudflare SQLite server.**
12. **Cloudflare-specific routing MUST stay outside the protocol semantics.**

## 3. Terminology

| Term | Meaning |
|---|---|
| `vaultId` | Portable cryptographic identity generated by the client. Never used as a Cloudflare routing identity. |
| `vaultHandle` | Backend-specific opaque routing handle. On SupaTabs Cloud this will be a Durable Object ID string. |
| `deviceId` | Random identifier for one browser installation. |
| `itemId` | Random identifier for one synchronized opaque entity. |
| `revision` | Server-assigned vault-global monotonically increasing integer. |
| `cursor` | Highest server revision the client has fully consumed. |
| `envelope` | Opaque wrapped `AccountKey` data. Server does not interpret cryptographic contents. |
| `tombstone` | A deleted item retained as a revisioned record. |
| `syncRequestId` | Unique ID for one sync request, used for safe retries. |

## 4. Reference deployment architecture

```text
Browser extension
       |
       | HTTPS + signed request
       v
Gateway Worker
       |
       | resolve vaultHandle
       v
SQLite-backed Durable Object
       |
       +-- vault metadata
       +-- devices
       +-- key envelopes
       +-- sync items
       +-- pairing mailbox
       +-- processed sync requests
```

For a simple BYO/development deployment, a single known/default Durable Object MAY represent the only vault.

The core Durable Object implementation MUST NOT depend on SupaTabs Cloud's future D1 customer database.

## 5. Cloudflare implementation requirements

Use **SQLite-backed Durable Objects**.

The implementation SHOULD use Durable Object SQLite synchronously for mutation transactions. Durable Object state that must survive eviction/restart MUST be persisted to SQLite, never only in memory.

The Worker gateway SHOULD be thin:

1. Validate protocol-level headers.
2. Resolve `vaultHandle`.
3. Forward request to the correct Durable Object.
4. Do not inspect ciphertext.
5. Do not perform per-sync D1 customer lookups.

The implementation SHOULD avoid keeping Durable Objects artificially alive. Normal sync is request/response and should allow the object to become idle.

## 6. Suggested SQLite schema

Exact SQL types may be adapted to Cloudflare SQLite, but semantics are normative.

### `vault_meta`

```sql
CREATE TABLE vault_meta (
    singleton INTEGER PRIMARY KEY CHECK (singleton = 1),
    protocol_version INTEGER NOT NULL,
    current_revision INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL
);
```

### `devices`

```sql
CREATE TABLE devices (
    device_id TEXT PRIMARY KEY,
    auth_algorithm TEXT NOT NULL,
    auth_public_key BLOB NOT NULL,
    created_at TEXT NOT NULL,
    last_seen_at TEXT,
    last_cursor INTEGER NOT NULL DEFAULT 0,
    revoked_at TEXT,
    metadata_ciphertext BLOB
);
```

`metadata_ciphertext` MAY contain encrypted device name/browser metadata.

### `sync_items`

```sql
CREATE TABLE sync_items (
    item_id TEXT PRIMARY KEY,
    revision INTEGER NOT NULL UNIQUE,
    deleted INTEGER NOT NULL,
    crypto_version INTEGER,
    nonce BLOB,
    ciphertext BLOB
);

CREATE INDEX idx_sync_items_revision
ON sync_items(revision);
```

Rules:

- Active item: `deleted = 0`, nonce/ciphertext required.
- Tombstone: `deleted = 1`; ciphertext MAY be null.
- `revision` is always the latest revision of that item.

### `key_envelopes`

```sql
CREATE TABLE key_envelopes (
    envelope_id TEXT PRIMARY KEY,
    envelope_type TEXT NOT NULL,
    credential_ref TEXT,
    crypto_version INTEGER NOT NULL,
    nonce BLOB,
    ciphertext BLOB NOT NULL,
    created_at TEXT NOT NULL
);
```

`envelope_type` is an opaque/versioned discriminator such as:

- `recovery-v1`
- `device-v1`
- later: `passkey-prf-v1`

The backend does not derive or unwrap keys.

### `sync_request_results`

Used to make an entire sync POST retry-safe.

```sql
CREATE TABLE sync_request_results (
    device_id TEXT NOT NULL,
    request_id TEXT NOT NULL,
    request_digest BLOB NOT NULL,
    response_json TEXT NOT NULL,
    created_at TEXT NOT NULL,
    PRIMARY KEY(device_id, request_id)
);
```

Retention target: last 24 hours **or** last 64 requests/device, whichever is more useful for implementation. GC can be opportunistic.

If the same `(device_id, request_id)` is retried:

- Same request digest -> return stored response verbatim.
- Different digest -> reject with `request_id_reused`.

This avoids one deduplication row per mutation.

### `pairings`

```sql
CREATE TABLE pairings (
    pairing_id TEXT PRIMARY KEY,
    polling_secret_hash BLOB NOT NULL,
    public_key BLOB NOT NULL,
    human_code TEXT NOT NULL,
    state TEXT NOT NULL,
    transfer_payload BLOB,
    created_at TEXT NOT NULL,
    expires_at TEXT NOT NULL
);
```

Allowed states:

- `pending`
- `approved`
- `consumed`
- `cancelled`

Pairing records MUST expire automatically/opportunistically, target 10 minutes.

## 7. Revision model

The Durable Object owns one `current_revision`.

Every successful item mutation receives a distinct next revision:

```text
current_revision = 100

mutation A -> 101
mutation B -> conflict, no revision
mutation C -> 102

current_revision = 102
```

Revision values MUST NOT be generated by clients.

A record update MUST use compare-and-swap semantics:

- `expectedRevision = 0`: item MUST NOT already exist.
- `expectedRevision = N > 0`: current item revision MUST equal `N`.

A conflict MUST NOT modify the record or advance the revision counter for that mutation.

## 8. Sync semantics

### Endpoint

```http
POST /v1/sync
```

Requires authenticated device signature.

### Request

```json
{
  "protocolVersion": 1,
  "syncRequestId": "018f...",
  "cursor": 18291,
  "mutations": [
    {
      "itemId": "6dd...",
      "expectedRevision": 17211,
      "deleted": false,
      "cryptoVersion": 1,
      "nonce": "base64...",
      "ciphertext": "base64..."
    },
    {
      "itemId": "912...",
      "expectedRevision": 0,
      "deleted": true
    }
  ],
  "limit": 500
}
```

### Processing order

The server MUST:

1. Authenticate the device.
2. Check `syncRequestId` idempotency.
3. Validate request size/count limits.
4. In one logical mutation transaction:
   - apply each mutation independently;
   - assign revisions only to successful mutations;
   - preserve conflicts;
   - update `current_revision`;
   - update device `last_seen_at`.
5. Pull latest item states whose `revision > cursor`, ordered ascending, limited by `limit`.
6. Persist the complete response against `syncRequestId`.
7. Commit.
8. Return the persisted response.

A batch MAY contain both successful and conflicting mutations. One conflict MUST NOT reject unrelated mutations.

### Response

```json
{
  "protocolVersion": 1,
  "serverRevision": 18307,
  "nextCursor": 18302,
  "hasMore": true,
  "mutationResults": [
    {
      "itemId": "6dd...",
      "status": "ok",
      "revision": 18305
    },
    {
      "itemId": "912...",
      "status": "conflict",
      "current": {
        "itemId": "912...",
        "revision": 18297,
        "deleted": false,
        "cryptoVersion": 1,
        "nonce": "base64...",
        "ciphertext": "base64..."
      }
    }
  ],
  "changes": [
    {
      "itemId": "abc...",
      "revision": 18293,
      "deleted": false,
      "cryptoVersion": 1,
      "nonce": "base64...",
      "ciphertext": "base64..."
    }
  ]
}
```

### Cursor rule

`nextCursor` MUST equal:

- the greatest revision actually returned in `changes`, or
- the input cursor if no changes were returned.

`serverRevision` is informational and represents the vault's committed current revision.

`hasMore = nextCursor < serverRevision` after accounting for whether there are remaining rows newer than `nextCursor`.

The client MUST continue pulling until `hasMore = false`.

This prevents skipping records when responses are paginated.

## 9. Why `sync_items` doubles as the change index

No permanent operation log is required for v1.

Because every item stores its **latest** revision:

```sql
SELECT *
FROM sync_items
WHERE revision > ?
ORDER BY revision
LIMIT ?;
```

returns every item whose current state changed after the client's cursor.

If one item changed at revisions 101 and 105 while a device was offline, the device only needs the state at 105.

This is intentional.

## 10. Tombstones

Deletes MUST be represented as tombstones.

Do not physically delete synchronized items in v1.

Reason:

```text
offline device has item X @ revision 40
another device deletes X @ revision 90
offline device reconnects later
```

Without a tombstone, the old device could resurrect X.

A tombstone must preserve:

- `itemId`
- deletion revision
- deleted flag

In the normative Phase 1 BYO profile, tombstones are terminal. Even a mutation whose `expectedRevision` matches the latest tombstone MUST conflict if it attempts to make that `itemId` active. Restored content uses a new `itemId`.

V1 MAY retain tombstones indefinitely.

Future GC may remove tombstones only when correctness can be proven using all non-revoked device cursors plus a safety retention window.

## 11. Device authentication

### Device keys

Each extension installation creates a separate asymmetric authentication keypair.

Recommended v1 algorithm:

- ECDSA P-256
- SHA-256
- WebCrypto-compatible representation

The server stores only the public key.

Do not reuse this key for encryption.

### Request signature

Implement a **small documented profile of RFC 9421 HTTP Message Signatures** rather than an ad-hoc signature format.

At minimum bind:

- HTTP method
- target path + query
- content digest for requests with a body
- creation time
- expiration time
- `deviceId`
- `vaultHandle`
- unique request identifier

Target validity window: approximately 5 minutes.

The server MUST reject:

- invalid signatures;
- revoked devices;
- expired signatures;
- unsupported algorithms;
- body digest mismatch.

Normal `/sync` correctness MUST still rely on idempotent `syncRequestId`, not merely signature timestamps.

### Sensitive operations

Phase 1 may authorize sensitive operations using a currently trusted device key.

Phase 3 will add fresh passkey/WebAuthn authorization for high-risk cloud-account operations.

## 14. Pairing API

Pairing is a temporary encrypted mailbox; the server never receives plaintext `AccountKey`.

### Create pairing

```http
POST /v1/pairings
```

May be unauthenticated but MUST be rate-limited.

Request:

```json
{
  "protocolVersion": 1,
  "transferPublicKey": "base64...",
  "device": {
    "deviceId": "...",
    "authAlgorithm": "ecdsa-p256-sha256",
    "authPublicKey": "base64-SPKI-DER",
    "metadataCiphertext": null
  }
}
```

Response:

```json
{
  "pairingId": "...",
  "pollingSecret": "...",
  "humanCode": "481729",
  "expiresAt": "..."
}
```

Store only a hash of `pollingSecret`.

### List pending pairings

```http
GET /v1/pairings/pending
```

Authenticated trusted device.

### Approve

```http
POST /v1/pairings/{pairingId}/approve
```

Authenticated trusted device.

Body contains only client-produced opaque encrypted transfer data. Approval atomically registers the proposed device identity supplied when the pairing was created.

### Poll

```http
GET /v1/pairings/{pairingId}
Authorization: SupaTabs-Pairing <polling-secret>
```

New device polls using its secret.

### Consume

Polling does not consume the packet. After the new device successfully obtains it, call:

```http
POST /v1/pairings/{pairingId}/consume
Authorization: SupaTabs-Pairing <polling-secret>
```

Consumption is idempotent and removes the transfer payload promptly.

## 17. Protocol/version separation

Keep these independent:

### Sync protocol version

Defines HTTP/API semantics.

```text
SupaTabs Sync Protocol v1
```

### Crypto version

Stored beside ciphertext; interpreted by the extension.

```text
cryptoVersion = 1
```

The backend only preserves the value.

### Vault/application format

Lives *inside* ciphertext and is entirely client-owned.

A new tab/group schema MUST NOT require a backend protocol update.

## 23. Phase 1 acceptance criteria

Phase 1 is complete when:

- A fresh backend can be bootstrapped without Phase 3.
- Two devices can authenticate using independent device keys.
- Devices can push/pull opaque encrypted items.
- Concurrent edits to separate items do not conflict.

- A device can be revoked.

## 25. Normative Phase 1 BYO profile

This section resolves the implementation choices left open by the preceding general specification. It is normative for the Phase 1 single-vault BYO server.

### 25.1 Single-vault routing and discovery

Each deployment has exactly one named default Durable Object. The default name is deployment configuration and is not derived from `vaultId`.

Before setup, `GET /v1/info` initializes only server metadata and returns `setupRequired: true`. Its `serverId` MUST remain stable across Durable Object eviction and Worker deployments. After setup it also returns the non-secret default `vaultHandle`, allowing recovery from a lost bootstrap HTTP response.

Successful bootstrap returns the portable `vaultId`, backend-specific Durable Object ID string as `vaultHandle`, and registered `deviceId`. After bootstrap, authenticated gateway routes MUST accept only that default object's exact handle. Other syntactically valid Durable Object IDs MUST return `vault_not_found` and MUST NOT create new objects.

### 25.2 Bootstrap wire contract

```http
POST /v1/bootstrap/device
Authorization: Bearer <high-entropy-setup-token>
Content-Type: application/json
```

```json
{
  "protocolVersion": 1,
  "vaultId": "portable-vault-id",
  "device": {
    "deviceId": "first-device-id",
    "authAlgorithm": "ecdsa-p256-sha256",
    "authPublicKey": "base64-SPKI-DER",
    "metadataCiphertext": null
  }
}
```

`authPublicKey` is a padded RFC 4648 base64 encoding of an ECDSA P-256 SubjectPublicKeyInfo DER value. Bootstrap MUST validate that WebCrypto can import it for ECDSA verification.

The configured setup token is accepted only while `bootstrap_completed_at` is null. The device insert and bootstrap marker update MUST be one transaction. Once completed, all later bootstrap calls return `setup_already_completed`, including calls presenting the original token. Operators SHOULD delete the Cloudflare secret after bootstrap.

### 25.3 SupaTabs RFC 9421 signature profile

Authenticated requests MUST contain:

- `X-SupaTabs-Device-Id`;
- `X-SupaTabs-Vault-Handle`;
- `X-SupaTabs-Request-Id`;
- `Signature-Input` and `Signature` using label `sig1`;
- `Content-Digest: sha-256=:<base64>:` when the body is non-empty.

The covered component order is fixed:

```text
"@method" "@path" "@query"
["content-digest" when a body is present]
"x-supatabs-device-id"
"x-supatabs-vault-handle"
"x-supatabs-request-id"
```

`@method` is lowercase, `@path` is the URL pathname, and `@query` is the leading-question-mark query string or `?` when empty. Signature parameters MUST appear in this order:

```text
;created=<unix-seconds>;expires=<unix-seconds>;keyid="<deviceId>";alg="ecdsa-p256-sha256"
```

`keyid` MUST equal `X-SupaTabs-Device-Id`. The validity interval MUST be no longer than the configured five-minute default. Implementations MAY allow at most 30 seconds of clock skew. ECDSA signatures use SHA-256 and the WebCrypto P-256 signature representation. The request body digest covers the exact received bytes.

For `/v1/sync`, `syncRequestId` identifies protocol idempotency and `X-SupaTabs-Request-Id` identifies the signed HTTP request; clients MAY use the same value. Retrying a sync MAY produce a fresh HTTP signature but MUST preserve the exact JSON body and `syncRequestId`.

### 25.4 Final sync rules

- A request containing the same `itemId` more than once is `invalid_request`.
- `cursor` MUST NOT exceed the committed `serverRevision` at the beginning of the transaction.
- A tombstone is terminal in v1. A mutation attempting to make that `itemId` active is a conflict with code `tombstone_terminal`, even when `expectedRevision` equals the tombstone revision. Restoration requires a new `itemId`.
- If an expected nonzero revision names no existing item, the conflict's `current` value is `null`.
- Idempotency compares a SHA-256 digest of the exact request body. Identical reuse returns the stored JSON bytes verbatim; different reuse returns `request_id_reused`.
- Results are retained for no more than 24 hours and at most the newest 64 requests per device.
- Pull pagination stops at the first of the requested item limit, configured item limit, or configured serialized-response byte limit. `nextCursor` and `hasMore` retain the rules in section 8.
- If mandatory mutation/conflict results exceed the response byte limit, the transaction MUST roll back and return `response_too_large`; the client retries smaller mutation batches.

### 25.5 Device, envelope, and pairing rules

Revoking an already-revoked or unknown device is idempotent. Revoking the final active device returns `last_active_device`. Revoking the calling device is otherwise allowed when another active device remains.

Envelope `PUT` is an idempotent upsert and `DELETE` is idempotent. Phase 1 permits deletion of the final envelope because the backend cannot establish whether an opaque envelope is usable.

Pairing creation uses this body:

```json
{
  "protocolVersion": 1,
  "transferPublicKey": "base64-opaque-transfer-key",
  "device": {
    "deviceId": "new-device-id",
    "authAlgorithm": "ecdsa-p256-sha256",
    "authPublicKey": "base64-SPKI-DER",
    "metadataCiphertext": null
  }
}
```

Approval accepts `{ "transferPayload": "base64-opaque-payload" }` and atomically registers the proposed device, changes the pairing to `approved`, and stores the payload. Repeating the exact approval is idempotent; a different payload or invalid transition returns `invalid_pairing_state`.

Polling and consumption authenticate with:

```http
Authorization: SupaTabs-Pairing <polling-secret>
```

The polling secret MUST NOT appear in a URL. `GET /v1/pairings/{pairingId}` does not consume an approved payload. `POST /v1/pairings/{pairingId}/consume` changes `approved` to `consumed`, clears the payload, and is idempotent when already consumed.

### 25.6 Default operational limits

| Limit | Default |
|---|---:|
| Request body | 10 MiB |
| Decoded item/envelope/transfer ciphertext | 1 MiB |
| Mutations per sync | 500 |
| Returned changes | 1,000 |
| Serialized sync response | 1,500,000 bytes |
| Signature validity | 300 seconds |
| Pairing lifetime | 600 seconds |
| Pairing creation rate | 10/source/600 seconds |

The response limit stays below Cloudflare's SQLite row limit so `response_json` can be persisted as one row. All values are deployment configuration and are returned where relevant from `/v1/info`.

Additional stable error codes introduced by this profile are:

- `response_too_large`
- `tombstone_terminal`
- `last_active_device`
- `invalid_pairing_state`
- `not_found`

### 25.7 CORS and logging

The BYO gateway returns wildcard CORS without credentials and supports preflight for all protocol headers and methods. This does not authorize requests; cryptographic device authentication remains mandatory.

Production logs MUST contain only route templates/paths, method, status/error code, latency, sizes, counts, revisions, and hashed or truncated identifiers. Setup tokens, pairing secrets, keys, ciphertext, and plaintext application data MUST never be logged.
